# API security

The HTTP boundary is intentionally small, but several reusable hardening primitives already exist.

## Request identifiers

Every response receives an X-Request-ID value generated by the request-id middleware.

Clients can also send X-Correlation-ID. The current correlation helper only reads the value; propagating it into task metadata is an application responsibility.

## Body limits

The body-limit middleware caps request size before decoding. This protects the service from accidentally accepting unbounded payload bodies.

The limit policy lives in internal/api/limits.go.

## Security headers

Security-header middleware is available as a composable policy in internal/api/security_headers.go.

## CORS

CORS policy is isolated in internal/api/cors.go so deployments can tighten allowed origins without modifying handlers.

## Authentication

Authentication primitives live in internal/auth. The runtime itself does not enforce a credential policy because that is an API/deployment boundary decision.

Production deployments should place authentication/authorization before task-control routes. In particular, worker scaling, cancellation and DLQ recovery should not be exposed to unauthenticated clients.

## Idempotency

Idempotency keys prevent accidental duplicate submission within one process. They are not an authorization mechanism.

## Data handling

Task payloads are application data. Do not place secrets into payloads unless the storage and logging policy explicitly supports them. The bundled log executor prints payload content and is intended only as a development example.

## Single-node file storage

The file repository stores task payloads in plaintext JSON. It therefore inherits the host filesystem's access controls and backup exposure.

For production workloads containing sensitive data, use an encrypted/secured persistence adapter and a handler that does not log raw payloads.
